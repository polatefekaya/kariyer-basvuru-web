# UI Kit

Solid + Tailwind v4 port of the `kariyer-zamani-web` design language. Tokens live in
`src/index.css` (`:root` / `.dark` HSL variables → `@theme inline`), primitives come from
[Kobalte](https://kobalte.dev), icons from `lucide-solid`, animations from `tw-animate-css`.

```tsx
import { AppButton, AppInput, toast } from '@/components/ui'
```

**House rules:** `rounded-2xl` is the surface/control radius (nested elements one step down), compact pill controls (segmented, xs/sm buttons, badges, tabs) are `rounded-full`; no `shadow-*` anywhere (depth comes from borders + surface tokens); body text is `font-normal` and `font-medium` is the boldest tier (titles, headings, eyebrows only); every control is `select-none` with a pointer cursor (`cursor-not-allowed` when disabled,
`hover:` never fires on disabled — see the `hover` variant override in `index.css`). Hover colours always come from the hover tokens: text → `text-primary-hover`, primary/secondary surfaces → `bg-primary-hover` / `bg-secondary-hover` — never `text-foreground` or opacity tricks.

## Media / CDN

`src/lib/mediaUrl.ts` is a 1:1 port of `kariyer-zamani-web/src/utils/mediaUrl.ts`, so both apps emit identical
Cloudflare transform URLs and share the edge cache:

- `public/…` / `private/…` keys → `VITE_CDN_URL`; `cdnImage()` adds `/cdn-cgi/image/format=auto,quality=40[,width=<snapped>,fit=cover]/`.
- Legacy paths (`images/<uuid>-x.jpg`) → `VITE_API_URL`. `http(s):`, `blob:`, `data:` pass through.
- Widths snap to `WIDTH_LADDER` (64…2048) to bound unique transforms. `cdnImageSrcSet()` gives `1x/2x`.
- `private/…` keys are **not** served by the CDN — use a presigned URL from the file-service (`isPrivateKey()`).
- `src/lib/imageCache.ts` is the reactive valid/invalid memo shared by every `AppImage`/`AppAvatar`.

Env: copy `.env.example` → `.env` (`VITE_API_URL`, `VITE_CDN_URL`, `VITE_FILE_SERVICE_URL`).

## Data layer (`src/lib/api`, `src/lib/query.tsx`, `src/features/*`)

This app is the **employer portal / ATS**: the signed-in user is always a **company**; employees appear only as
**candidates** attached to applications.

Optimistic pattern (see `useSetApplicationStatus`):

```ts
onMutate:  ({ uid, status }) => patchApplications([uid], { application_status: status }),  // prefix-matched cache patch + rollback
onError:   (_e, _v, ctx) => ctx?.rollback(),
onSettled: invalidateAll,
```

In components: `const move = useSetApplicationStatus()` →
`<AppButton loading={move.isPending} onClick={() => move.mutate({ uid, status: 'under_review' })}>`.

`:id` params accept the legacy uid (`…-company` / `…-employee`) **or** the Supabase UUID. Endpoint shapes differ:
`/jobs/company/:uid`, `/job_applications/*/applications` and `/employee/:uid` **spread** the payload next to
`success`; `/company/:id`, `/jobs/:uid` and status mutations use `{ success, data }`.

## The recruiting service

The ATS half of the app talks to **kariyer-recruiting-service**, not to the Node backend:
`recruitingApi` in `src/lib/api/client.ts` (same Supabase bearer, `VITE_RECRUITING_API_URL`
origin, no `{ success, data }` envelope — it answers with the payload and
`{ error: { code, message, details } }` on failure).

| Feature                                                 | Talks to           |
| ------------------------------------------------------- | ------------------ |
| `applications` — pipeline, list, stats, notes, activity | recruiting service |
| `hiring` — interviews, interviewer directory            | recruiting service |
| `jobs`, `companies`, `candidates`, `resumes`            | Node backend       |

**Stages, not statuses.** `features/applications/stages.ts` holds the nine-stage vocabulary
(`NEW · REVIEWING · CONTACT · INTERVIEW · OFFER · HIRED · HOLD · REJECTED · WITHDRAWN`) with
Turkish labels, badge variants and the open/closed split. What a user may do is **not** decided
here: every list row carries `allowedActions` from the service, and the ⋯ menus render exactly
those. An illegal move answers 409 `INVALID_STATUS_TRANSITION`.

Inviting an applicant who is still `NEW` moves them to `INTERVIEW` through `REVIEWING` in one
call — the service does the walk, so the UI offers "Mülakata davet et" on every open row.

**Where applications come from.** Three sources, chosen in `features/applications/api.ts` and
`features/hiring/api.ts`:

1. **kariyer-recruiting-service** when `VITE_RECRUITING_LIVE=true` — the nine-stage pipeline with notes,
   interviews and the activity trail. It authorises every read against `public.job_application` /
   `company_job`, so it must see the same database as the portal's backend; a locally seeded service does not
   know a real job uid.
2. **the Node backend** otherwise, whenever there is a session (`features/applications/nodeApi.ts`) — real
   applications from `/job_applications/:jobUid/applications`, with `applicant_match.overall_match_percentage`
   as the score. It speaks the five statuses `job_application` stores, mapped to stages by
   `features/applications/legacy.ts` (pending→NEW, under_review→REVIEWING, accepted→HIRED, rejected→REJECTED,
   withdrawn→WITHDRAWN); only those four are offered as moves, because the others have no column to live in.
   The company-wide list is assembled per posting on purpose — `/job_applications/companies/:uid/applications`
   never reads the company filter it is given and answers with every application in the database.
3. **mocks** when there is no session at all.

`config.HAS_PIPELINE` (1 or 3) is what the screens check before rendering notes, the interviews tab, the
activity trail and the invite actions — without the service there is nothing behind them, and a notepad that
cannot save is worse than no notepad.

**Running the pipeline locally against real data.** The recruiting service authorises every read against
`public.job_application` / `company_job` in its own database, so a locally seeded one does not recognise a
real ilan uid and those screens stay hidden. `src/dev/atsBridge.ts` (dev-only, loaded from `index.tsx`)
closes that gap: with the portal signed in, run `await __kzSyncAts()` in the console and it copies this
company, its postings, applicants and applications into the service's stand-in tables through its
Development-only `POST /dev/stand-ins`. Nothing is written to the backend. Then set
`VITE_RECRUITING_LIVE=true` and restart the dev server — see `kariyer-recruiting-service/docs/LOCAL.md` §4.

**Mock mode** (`config.USE_MOCKS`): on with `VITE_USE_MOCKS=true`, or automatically in dev while
`VITE_SUPABASE_URL` is empty (no way to get a Bearer token then); never in production unless forced. `src/mocks/`
holds the deterministic generators (`data.ts`, shared with the dev catalogs — jobs, applicants, and per-uid
candidate profiles and CVs) and in-memory APIs with the same signatures: `jobsApi` / `companiesApi` /
`candidatesApi` / `resumesApi` mirror the Node backend, while `applicationsApi` / `hiringApi` mirror the
**recruiting service's response shapes exactly** (stages, `allowedActions`, the grouped interview board), so
turning mocks off changes where the data comes from and nothing else (filters, sorting, paging, status changes and deletes
persist for the session). The session store pretends to be a signed-in, approved company so the access gate opens;
the user card shows "Örnek veri modu". Set `VITE_USE_MOCKS=false` to hit the real backend while Supabase is
unconfigured (you'll land on the "Oturum açmanız gerekiyor" screen).

**The dev API proxy.** `VITE_API_URL` is a _relative_ path in dev (`/api`) and `vite.config.ts`
proxies it to `VITE_API_PROXY_TARGET`. The backend's CORS allow-list lives at its gateway and names
only the origins the other apps use — a preflight from any other port comes back 204 with no
`Access-Control-Allow-Origin`, so every request fails, the company lookup fails with it, and the
portal looks signed out. Proxying keeps dev requests same-origin and sidesteps that entirely. A
deployment sets an absolute `VITE_API_URL` and needs its origin on the gateway's list.

**No roles.** Every authenticated user of an approved company has the same access, and that is a
decision rather than a gap: the platform's auth has no role to map onto, so the authorisation
boundary is the company and it is enforced on every route
(`kariyer-recruiting-service/docs/PLAN.md`, "Roles are not coming"). Nothing in these screens
should gate on a role, hide a field per role, or assume a permission check exists.

**Signing in.** `goToLogin()` sends the browser to the shared auth hub with `?type=b` (şirket — the hub's
account-type ids are `c`/`b`/`a`/`co`) and `?redirect_to=<absolute url>`. The hub puts the session on that
url's hash (`#access_token=…&refresh_token=…`), which `initSession()` consumes and strips. Two things bite:
the parameter is `redirect_to`, not `redirect`; and the hub drops a `redirect_to` whose origin is not in its
own allow-list (`kariyer-auth-hub/src/types/config.ts`), silently, landing the user on the site's default page
instead of back here. That list has `localhost:3000` and `localhost:5173`; `localhost:5199` is added but needs
a hub deploy — until then, run `pnpm dev --port 3000` to complete a real login round-trip. The portal's
deployed origin has to go on that list too.

One thing to know when testing in an automated/background Chrome tab: `IntersectionObserver` callbacks only run
while the document is visible (`document.hidden === false`) — a hidden tab never loads the next page or the
applicants previews until it renders a frame.
